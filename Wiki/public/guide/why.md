# 왜 이렇게 만들었나

## AI 에게 필요한 콘텐츠 작업 흐름

AI가 콘텐츠를 고치려면 **무엇을 만들 수 있는지 조회하고, 변경 결과를 확인하는 방법**이 필요합니다.

| 작업 | 이 엔진의 방식 | 현재 상태 |
|---|---|---|
| 게임플레이 작성 | 선언적 규칙 문서 | 문법·인자 검증 가능, 실행기는 개발 예정 |
| 콘텐츠 정의 | 스키마가 있는 YAML/JSON | 구현됨 |
| 변경 결과 확인 | `alice check`의 구조화 진단 | 구현됨 |
| 실행 중인 세계 읽기 | World를 문서로 덤프 | SID-05에서 구현 예정 |

검증 없이 반복하면 오류가 쌓입니다. 확인이 왕복 한 번에 끝나야 AI 가 일할 수 있습니다.

## JSON 이라고 다 AI 친화가 아니다

참고한 엔진 중 Piccolo 는 애셋을 이미 JSON 으로 저장합니다. 열어보면 이렇습니다.

```json
{ "convert": [1, 7, 55, 29, 33, 34, 35, 36, 37, ...] }
```

사람도 AI 도 이 배열이 무엇인지 알 수 없습니다. 스키마도 설명도 없습니다.

**형식이 아니라 모양이 문제입니다.** 그래서 이 엔진은 형식(YAML/JSON)이 아니라
다음 넷을 핵심으로 잡았습니다.

1. **스키마** — 무엇을 쓸 수 있는지가 기계가 읽는 형태로 정의된다
2. **설명과 예시** — 모든 필드에. AI 는 설명 열 줄보다 예시 하나에서 더 배운다
3. **진단** — 틀렸을 때 위치와 **고치는 법**을 함께 준다
4. **왕복** — 읽고 → 고치고 → 되쓰고 → 다시 읽는 고리가 닫힌다

## 스크립트 언어를 만들지 않은 이유

게임 엔진은 대개 스크립트 언어를 하나 갖습니다. 우리는 안 만들었습니다.

**언어를 하나 더 만들면 AI 가 배울 것이 하나 더 늘어납니다.**
그리고 그 언어의 오류는 런타임까지 가야 드러납니다.

대신 두 가지로 나눴습니다.

```yaml
rules:
  - when: input.pressed("Jump") and physics.grounded    # 읽기만
    do:
      - physics.impulse: { direction: [0, 1, 0], force: 6.5 }   # 쓰기만
```

- `when:` — **부작용 없는 식.** 대입할 수 없다
- `do:` — **유한한 동사 목록.** `alice verbs` 로 전부 나온다

### 이 분리가 주는 것

**조건 판단과 상태 변경을 분리합니다.** 같은 프레임의 조건을 같은 상태에서 판단한 다음
동작을 적용하는 것이 Runtime의 목표입니다. 조건식이 읽기 전용이라는 사실만으로
여러 동작의 실행 순서까지 독립적이 되는 것은 아닙니다. 서로 다른 규칙이 같은 값을 쓰는 경우의
적용 순서와 충돌 정책은 Runtime에서 정하고 테스트해야 합니다.

**정적으로 전부 검사됩니다.** 실행 전에 이미 압니다.

- 모든 동사가 실재하고 인자가 맞다
- 모든 이름이 읽을 수 있는 것이다
- 함수와 값을 혼동하지 않았다
- 인자 개수가 맞다

## 진단이 제품 기능인 이유

보통의 검증기는 이렇게 말하고 끝납니다.

```
Error: field 'positon' is not allowed
```

AI 는 스키마 전문을 다시 읽어야 하고, 대개 다른 곳을 고칩니다.

여기서는 이렇게 말합니다.

```
player.actor.yaml:12:5: error[schema.unknown_field]: 'positon' 은 Transform 에 없는 필드다
  |       positon: [0, 1, 0]
  |       ^
  = 'position' 을(를) 뜻한 것인가? 쓸 수 있는 필드: position, rotation, scale
```

**위치 + 안정 코드 + 오타 제안 + 후보 목록.** 이 한 덩어리가 AI 한 번의 수정으로 이어집니다.

이래서 YAML 파서를 직접 썼습니다. 서드파티 파서로는 이 품질을 낼 수 없습니다.

## 서드파티를 0으로 만든 이유

참고 엔진 10개를 이 머신에서 빌드해 봤습니다. **6개가 첫 빌드에서 막혔습니다.**
전부 서드파티나 생성 스텝에서 난 문제였고, 엔진 자체 코드의 문제가 아니었습니다.

그래서 YAML 파서, JSON 파서, 테스트 프레임워크를 직접 썼습니다. 합쳐서 3,000줄 남짓입니다.
**그 비용이 "클론하면 바로 빌드된다"보다 싸다고 판단했습니다.**

## 단점

이 설계에도 대가가 있습니다. 숨기지 않겠습니다.

| 단점 | 왜 감수하는가 |
|---|---|
| 표현력이 스크립트 언어보다 낮다 | 못 하는 것이 나오면 **동사를 추가**한다. 그러면 AI 도 그 능력을 즉시 얻는다 |
| YAML 전체 명세를 지원하지 않는다 | 앵커·태그·복합키는 게임 콘텐츠에 필요 없고, 있으면 AI 가 헷갈린다 |
| 텍스트 파싱에는 비용이 든다 | 우선 개발 중의 반복 속도를 중시한다. 런타임과 애셋 캐시는 후속 작업이다 |
| 파서를 직접 유지해야 한다 | 대신 진단 품질을 완전히 통제한다. 이 엔진에서는 그게 제품이다 |
| 동사 목록이 유한하다 | 그게 요점이다. 무한하면 AI 가 추측하기 시작한다 |
